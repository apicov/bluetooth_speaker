# The SBC link, and why I2S was abandoned

The bridge forwards **undecoded SBC over UART**. It does not decode audio at all.

```
phone ──A2DP/SBC──▶ bt_bridge ──SBC over UART──▶ hub ──▶ DAC + LEDs
                    no decode      1 wire          decodes here
```

**Status: working.** Sustained ~44,050 Hz effective against 44,100 nominal, link
clean, playback buffer stable at ~145 ms under closed-loop control.

---

## Why not I2S

The first design sent decoded PCM over I2S, bridge as master and hub as slave.
It silently lost **~1.15% of frames**, and finding out why took a long time. The
sequence of eliminations is worth recording, because almost every intuition was
wrong.

| Suspect | Ruled out by |
|---|---|
| Bridge clock wrong | Logic analyser: WS exactly 44,100 Hz |
| I2S driver broken | Self-loopback on one board: zero loss over 45 s |
| WiFi / DMA bandwidth | Loopback with no WiFi loses identically |
| Visualiser / CPU load | 577/s before, 577/s with it disabled |
| Read scheduling | Max read gap only 0.7% above average -- no stalls |
| WS signal integrity | Hardware edge counter: 44,099, exact |
| BCLK ringing | Edge-ratio counter: 32.000, exact |
| Grounding | Extra ground wires: only 12% better |
| **Asynchronous slave clocking** | **Inverting clock ownership: loss to zero** |

**The ESP32's I2S slave receiver drops frames when sampling a clock generated by
a different chip's crystal.** Everything on the wire was perfect; the peripheral
simply did not deliver what arrived at its pins.

Inverting ownership (hub as I2S master) fixed the frame loss completely but
broke bit alignment instead: the slave then has to drive data into a round trip
-- master clocks, slave sees it, slave drives, master samples -- that must close
inside half a bit period. It does not, across two boards. So the fix relocated
the problem rather than solving it.

UART sidesteps the whole category. Each byte self-synchronises on its start bit
and tolerates percent-level clock differences by design, so **no clock is
shared** and the failure mode cannot occur. It also carries a quarter of the
bytes and needs one signal wire instead of three.

## Wiring

|---|---|---|
| GPIO 25 (UART TX) | GPIO 23 (UART RX) | the only signal |
| GND x4 | GND x4 | keep them all |

Grounds still matter: this link would not run reliably above 500 kbaud on
breadboard jumpers.

## Baud rate

**500 kbaud.** 50 kB/s against ~42 kB/s of payload -- 84% utilisation, tighter
than anyone would choose, and chosen because these leads will not carry more:

| Baud | Result, per 5 s window |
|---|---|
| 1,000,000 | ~50% of packets corrupt |
| 750,000 | 20-30 bad sync, 15-20 CRC errors |
| **500,000** | **0-2 bad sync, 0-1 CRC errors** |

That ceiling is a property of the wiring, not the protocol. Packets are ~830
bytes, so a bit error rate of only 0.013% loses half of them -- large packets
amplify a small BER. Proper leads would lift it; so would SPI, which has ~30x
the headroom, though it reintroduces a clocked link.

Defined once in `components/dancefloor_sync/include/sbc_link.h`; both ends
include it and must agree.

## Wire format

```c
struct {
    uint8_t  sync0, sync1;   /* 0xA5 0x5A */
    uint16_t len;            /* payload bytes */
    uint32_t seq;            /* assigned at ENQUEUE, see below */
    uint8_t  checksum;       /* XOR of payload */
} /* followed by len bytes of SBC */
```

One A2DP packet holds several SBC frames back to back, so the hub decodes until
the payload is exhausted.

**`seq` is assigned when the packet is queued, not when it is transmitted.** The
first version numbered at transmit time, so a packet dropped by a full queue
never got a number and the hub saw an unbroken sequence -- drops were completely
invisible, and `gaps 2` was reassuring and meaningless.

## Three bugs that each looked like a link fault

**Byte-at-a-time resync.** The receiver hunted for the sync word with one
`uart_read_bytes()` call per byte. After a CRC error it rescanned ~660 bytes of a
corrupt packet that way -- tens of thousands of driver calls per second, backing
up the RX buffer and causing further corruption. Errors fed errors. It now bulk
reads into a 4 kB buffer and scans in memory.

**Undersized input buffer.** `streamer_feed()` drops silently when full, and one
A2DP packet decodes to ~3.5 kB of PCM in a single burst against an 8 kB buffer.
Audio was being discarded *after* a link that measured perfectly clean, which is
why every transport-level investigation kept coming back innocent. Now 32 kB.

**Over-eager stream-stop detection.** A 100 ms gap in the input was treated as
"stream ended", which restarts the presentation timeline *and empties the
playback ring*. SBC arrives in bursts and occasional multi-packet gaps exceed
100 ms, so this fired during ordinary playback and threw away ~200 ms of good
audio each time. The ring never settled and the servo never stopped chasing. Now
500 ms.

The common thread: each produced symptoms indistinguishable from a bad link, and
each was found only by adding a counter for the specific thing being lost.

## Reading the log

```
I sbc_in: pkts 252 | 44100 Hz x2 | eff 44050 Hz | sync 0 crc 0 gaps 0 dec 0 | fed-drop 0 B
```

| Field | Meaning |
|---|---|
| `pkts` | packets accepted in the window; ~250 per 5 s is normal |
| `44100 Hz x2` | read from the SBC frame header, not measured or inferred |
| `eff` | **PCM samples/s actually reaching playback** -- the number that matters |
| `sync` / `crc` | link integrity; single digits are fine, tens are not |
| `gaps` | packets the bridge dropped, visible because `seq` is set at enqueue |
| `fed-drop` | PCM discarded because the input buffer was full; must be 0 |

`eff` is the honest health metric. Everything else can look perfect while audio
quietly goes missing further down.

## Still to do

The hub decodes to PCM and multicasts **PCM** to satellites, so the WiFi link
still carries 1.4 Mbps. Forwarding SBC over the air would quarter the airtime and
let satellites hold four times the buffer for the same memory. It requires the
satellite to decode, which the shared `sbc_decoder` component already supports.
